I asked an AI agent to move a small service from Spring Boot 3.5 to 4.1.1. The agent renamed the starter coordinates, fixed the `@MockBean` removals, and reported `BUILD SUCCESS` in a few minutes. Hibernate 6 became Hibernate 7 somewhere in that version bump, and I barely noticed it in the agent's summary. That was the mistake. Hibernate 7 is not another ORM point release; it is the part of a Boot 4 upgrade where the build goes green and the data quietly stops meaning what it used to.

This is not a migration guide. The human-written guides are already good, and I link to them below. This is the part they do not write: what an AI agent misses when it does the upgrade for you, measured the way I measured the rest of the [Spring Boot 4 migration](/blog/spring-boot-4-migration-ai-agents/) — by refusing to trust the green build and diffing what actually changed.

## The first silent swap: your column names moved

Hibernate 7 changed its physical naming strategy. The strategy that turns a Java field name into a database column name now splits a digit that sits in front of a capital letter. A field called `v2Token` used to map to `v2token`. On Hibernate 7 it maps to `v2_token`. The same change hits `base64Content`, which becomes `base64_content`.

I did not read this in a changelog. I built the exact same entity on both versions and read the DDL each one emitted.

```sql
-- Boot 3.5.16 / Hibernate 6
create table event (
    id bigint generated by default as identity,
    occurred_at TIMESTAMP WITH TIME ZONE,
    base64content varchar(255),
    v2token varchar(255),
    primary key (id)
)

-- Boot 4.1.1 / Hibernate 7
create table event (
    id bigint generated by default as identity,
    occurred_at TIMESTAMP WITH TIME ZONE,
    base64_content varchar(255),
    v2_token varchar(255),
    primary key (id)
)
```

Same Java class. Same `@Column(name = "base64Content")` on the first field. The column name changed anyway. The strategy applies to explicit names too, which is the part that surprises people who thought writing `@Column(name = ...)` locked the column down. It did not.

| Java field | Hibernate 6 column | Hibernate 7 column |
|---|---|---|
| `base64Content` (explicit `@Column`) | `base64content` | `base64_content` |
| `v2Token` (no explicit column) | `v2token` | `v2_token` |

## Why this stays silent until production

Here is the trap that swallows an AI agent. If you let the agent run its tests against an in-memory H2 database, that database is created from the entities on every run. The schema is regenerated with the new names, so the new names match the new mapping, and every test passes. The build is green. The agent's `BUILD SUCCESS` is a true statement about compilation and schema generation against an empty database.

Your production database was not generated from the entities this morning. It was generated under Hibernate 6, with `v2token` and `base64content`. After the upgrade, Hibernate 7 expects `v2_token` and `base64_content`. If a column is missing, the first write or read against the real schema fails — not in the agent's test run, but on the first request after deploy. The gap is not a bug in the agent's edits. It is that the evidence the agent would need, your real schema, is not in the repository, so it never reaches the model.

This is the same structural hole I hit with [configuration keys that stopped binding](/blog/codex-spring-boot-4-yml-properties/) and [dependencies that resolved but wired nothing](/blog/codex-spring-boot-4-dependencies-silent-failures/). Boot 4's risk is rarely the thing that fails loudly. It is the thing that fails only where the agent cannot see.

## A real migration that broke exactly like this

I am not the first person to walk into this. The ejbca-ng-connector project hit it on a real upgrade: an entity mapped its certificate content with `@Column(name = "base64Content")`, and the migration script had created the column `base64content` under Hibernate 6. After moving to Spring Boot 4.1, Hibernate 7 generated `base64_content`, and saving certificates failed with `column "base64_content" of relation "discovery_certificate" does not exist`. Their tests ran on H2 with Flyway disabled, so the schema came from the entities and matched any column name — the tests stayed green, and the bug only appeared against the real database. That is the entire pattern in one GitHub issue ([ejbca-ng-connector #156](https://github.com/OmniTrustILM/ejbca-ng-connector/issues/156)): green tests, broken production, a column name nobody rechecked.

## The second silent swap: native query return types

The column rename is the easy one to explain. The return-type change is the one that compiles clean and throws at runtime. When you write a native query and pull a scalar back by hand, Hibernate 7 returns a different Java type than Hibernate 6 did.

```java
@Query(value = "select occurred_at from event where id = ?1", nativeQuery = true)
Optional<Object> findOccurredAtRaw(Long id);
```

On a `TIMESTAMP WITH TIME ZONE` column, Hibernate 7 hands back `java.time.OffsetDateTime`. Code that does this still compiles:

```java
Object raw = repo.findOccurredAtRaw(id).get();
java.util.Date when = (java.util.Date) raw; // compiles, then ClassCastException at runtime
```

The result is typed as `Object`, so the cast is legal at compile time. At runtime the actual type is `OffsetDateTime`, and the cast fails. An agent reviewing or writing that code sees a cast that the compiler accepts, because the compiler accepts every cast from `Object`. Nothing in the build tells it the runtime type changed. On a real PostgreSQL column the difference is sharper than on H2, which is why this one bites hardest in production and softest in the agent's test container. A Tolgee engineer hit the same wall on a real upgrade: native queries that selected a SQL `TIMESTAMP` started returning `LocalDateTime` where the old code expected `java.util.Date`, and again the cast compiled and failed at runtime ([Dmitrii Bocharov, Tolgee](https://www.linkedin.com/posts/bdshadow_springboot-hibernate-kotlin-activity-7486360486339506177-SArR)).

## The swaps I only caught by reading, not by running

Two more Hibernate 7 behavior changes did not show up in my tiny H2 experiment, but they are documented by people who hit them on real databases, and they belong in the same bucket.

The first is timezone storage. Hibernate 7 changes the default for `hibernate.timezone.default_storage`. Under Hibernate 6 the default normalized timestamps toward UTC; under Hibernate 7 the default keeps the offset. If your old rows were stored as plain UTC instants and your new reads interpret them with an offset, old data comes back shifted, with no error and no log line.

The second is performance. A team at Zooz reported that the same queries ran five to ten times slower after the Boot 4 upgrade pulled in Hibernate 7, with every health check and database dashboard insisting nothing was wrong ([Zooz Engineering](https://engineering.zooz.com/codetodeploy/hibernate-7-slow-queries-4907e3f8b9c2)). The SQL was faster; the cost had moved into entity hydration, which their monitoring did not watch. Every integration test stayed green, because tests assert correctness, not latency. A regression with no error and no log is the purest form of the silent failure this whole series is about.

## The pattern, again, on the persistence layer

I keep landing on the same split, and Hibernate 7 is where it shows up on the database side. There are changes a coding agent is genuinely good at: package renames, removed APIs, the `@MockBean` to `@MockitoBean` swap, the `@Where` to `@SQLRestriction` move. Those are loud. The compiler yells, the agent fixes, the compiler confirms, and that half of the upgrade is real progress.

Then there are the changes that compile fine and break later: a column name that shifted, a query return type that changed, a timezone default that flipped, a query that got ten times slower. Those are silent. The agent's `BUILD SUCCESS` covers the loud half completely and the silent half not at all, which is exactly what I measured across the [migration walkthrough](/blog/claude-code-spring-boot-4-migration-walkthrough/) — Claude Code and Codex both fix what the compiler can see and leave what it cannot, and on the silent layer the regression reflex that helps on the loud layer does nothing, because a silent failure is green on both the old version and the new one.

## What I do now

Four habits, specific to the persistence layer, on top of the ones I already run for the rest of the upgrade.

1. **Diff the DDL before and after, against a real schema copy.** I generate the schema on Boot 3.5 and on Boot 4.1.1, then run that diff against a restored copy of the production database, not an in-memory one. The column-name split showed up in the first diff and would have been invisible against a regenerated H2 database.
2. **Turn on `spring.jpa.hibernate.ddl-auto=validate` in staging.** It makes schema drift a hard startup failure instead of a quiet write error after deploy. The same flag also catches the timezone and return-type surprises earlier than a passing test suite does.
3. **Treat the agent's green build as a statement about compilation only.** When the agent says done, I still diff the DDL and I still run the app against a real database. The [Java and AI hub](/blog/ai-for-java-developers/) collects every measurement in this series, and the column rename is the piece that was missing from the persistence layer until now.

4. **Dump the DDL to a file instead of standing up a database.** Hibernate can write the generated schema to disk with `spring.jpa.properties.jakarta.persistence.schema-generation.scripts.action=create` and `spring.jpa.properties.jakarta.persistence.schema-generation.scripts.create-target=./schema.sql`. I run that on both versions and `diff` the two files; the column-name split lands in the patch with no database required. It is faster than provisioning a staging instance and catches the same class of drift, and it is the check I hand to an agent when I want it to verify the schema without me restoring a backup first.

If you are letting an agent do your Boot 4 upgrade, the column names are the cheapest place to get burned and the easiest to check. Generate the schema both ways, diff it, and do not let a green build talk you out of reading the diff. The fix once you see the rename is small — align the column, or pin the name in the mapping — but you will only write that fix if the diff is in front of you. An agent left to its own devices will ship the green build and call it done, because from where it sits, it is done.
